# 台日一番賞價格監測系統｜15 分鐘講稿提要

總長約 **14 分鐘**；保留約 1 分鐘給轉場與老師插問。

## 第 1 頁｜題目與定位（55 秒）

我們做的是台日一番賞價格監測系統。第一階段只接 Rakuten，把刊登價格保存成歷史快照，再提供價格觀察和跨境成本試算。它是套利可行性分析的 MVP，不保證獲利。

追問可補：唯一自動資料源是 Rakuten，目前沒有台灣成交價資料。

## 第 2 頁｜問題（80 秒）

同一角色在樂天有很多刊登，單看一筆價格容易失真；只看今天也看不到趨勢。更重要的是，日本價格低不代表帶回台灣後還有空間，因為有匯率、代購、物流與平台費。

追問可補：所以我們沒有直接宣稱發現套利，而是先做可重複觀察的資料鏈。

## 第 3 頁｜系統流程（95 秒）

爬蟲讀取啟用的追蹤角色，用日文關鍵字向 Rakuten 查詢。資料清洗後寫入 MySQL；Flask 再將最新快照與歷史資料顯示於網站，由 Chart.js 畫圖。

追問可補：目前沒有 Docker、排程或自建 REST JSON API。

## 第 4 頁｜資料模型（85 秒）

核心有三張表：tracked_items 管追蹤對象、listings 管實際商品 URL、price_snapshots 管每次觀測價格。重點是不覆蓋最新價，而是保存歷史。

追問可補：schema 目前沒有 README 提到的 alerts 表。

## 第 5 頁｜資料取得與清洗（85 秒）

爬蟲解析名稱、價格、URL、圖片、商店和庫存；排除套組、預購、福袋與不合理價格。商品 URL 唯一，同一天同一商品不重複新增快照。

追問可補：日本國內運費欄位尚未自動取得，成本頁需人工輸入。

## 第 6 頁｜核心分析（105 秒）

我們用每日中位數，而不是平均數，避免一筆極端高價主導整體。至少兩個資料日時，程式比較最新和前一日的中位數；若上升達 15%，顯示潛在漲幅預警。這只是觀察訊號。

追問可補：目前沒有 48 小時、最少 5 筆樣本或預警保存的實作。

## 第 7 頁｜跨境成本試算（95 秒）

輸入日圓商品價、運費、匯率、代購費、國際運費、平台費和預估售價後，系統會算落地成本、保本售價與預估淨利。日本比較便宜不等於有利潤，這一頁就是把假設攤開。

追問可補：預估售價與各費率是使用者輸入，不是系統自動查得。

## 第 8 頁｜Demo（90 秒）

先開首頁看追蹤商品與 Rakuten 連結；點進角色後看每日中位數、單筆狀態與兩日訊號；最後到成本試算器。若資料不足兩個資料日，就展示「資料不足」，不要硬解讀趨勢。

追問可補：截圖只是本機系統畫面，不應被當成市場統計結論。

## 第 9 頁｜成果與限制（95 秒）

完成的是 Rakuten 查詢、清洗、MySQL 快照、Flask 頁面、中位數、簡易訊號與成本公式。但目前只有單一刊登價資料源，沒有台灣資料，不能證明套利。

追問可補：`test_data.sql` 是本機測試資料，不能當市場成果。

## 第 10 頁｜NEXT（75 秒）

下一步不是急著加 ML，而是先讓資料可信：排程累積快照、補台灣可比資料、保存預警並加入樣本與時間窗條件，最後再檢驗跨市場關係。

追問可補：這樣能避免資料不足時產生過度結論。
